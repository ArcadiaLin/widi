# Background Job 持久化设计

面向 `apps/widi/src/core/background/`。前置阅读：`docs/ZH/persistence.md`。

本文只描述设计与顶层接口，不含实现。

---

## 1. 要解决的问题

一个 background job 对模型说两次话：

- **t0**：工具调用超时进入后台，立刻返回一个句柄，告诉模型「结果稍后作为一条独立消息到达」。
- **t1**：job 结束后，投递一条消息把结果交给模型。

t0 是一条落在会话分支上的工具结果。**它是一个悬着的承诺。** 只要 t1 没有到达，这条承诺就一直挂在上下文里，而模型没有任何办法判断它是「还在跑」还是「永远不会有结果了」。

会有三类情况让 t1 永远不到：进程被杀、agent 被 dispose、分支被 fork 走。

现有实现（`journal.ts` 的 sidecar 日志 + resume 时在分支文本里搜索 header 前缀）在这三类情况下都只能**事后推断**：分支上有 t0、找不到匹配的 t1，就认为它还欠着。这是拿「没有信息」当信息用，脆弱且不可追溯——文本被模型复述、被 compaction 改写、被用户粘贴，判断就错了。

**本设计的核心决定：闭合是一件被主动写下来的事，不是被推断出来的事。**

---

## 2. 状态归分支所有

job 状态接入 `docs/ZH/persistence.md` 描述的 persistence 层，namespace 为 `core:jobs`。

每一次 job 的生命周期转移，都在会话分支上追加一条 persistence ref，指向 custom storage 里的一条不可变记录。由此免费获得三条性质：

- **回退**：回退到 job 启动之前，那条 ref 不在分支上，这个 job 就不存在。不会给一条从未启动过它的分支投递结果。
- **分叉**：fork 一条分支自动带走它能看见的全部 job 状态，看不见的一条都不带。
- **可追溯**：ref 链就是这个 job 在这条分支上的完整历史，包括它是怎么结束的。

### ref 不进模型上下文

persistence ref 是 `custom` 类型的 entry。会话条目投影成模型上下文时，`custom` 条目**只有注册了对应的 entry projector 才会产生消息**，否则产出空。`core:jobs` 的 ref 不注册 projector。

所以 ref 是纯索引：它在分支上、参与回退和分叉、可被 fork 复制，但一个 token 都不进模型的上下文。写 ref 的成本只有文件体积。

> 这也留了一个后门：将来若要让模型知道「你还有几个 job 开着」，可以给 ref 类型注册一个 projector，**从已经写下的同一条 ref 投影出来**，不需要改变任何写入行为。

## 3. 记录模型

### 3.1 转移链，不是全量快照

state root 指向**最新一条转移记录**，记录通过依赖声明链回上一条。custom storage 在解析时沿链回溯，reduce 成 job 表返回。

选链而不是快照，理由有三：

1. 写下的就是「开始、结束、闭合」这件事本身，不是被状态变更逼出来的整表重写。
2. 回退到分支中途某条 ref 时，从那里回溯得到的链前缀，天然就是那一刻的正确历史。这就是可追溯性。
3. fork 闭包沿依赖走，整条历史一起被带走，不需要额外声明。

### 3.2 三种记录

```
started  — job 进入后台。携带身份（jobId、toolCallId、工具名、调用方给的名字、
           origin、时间戳）与它的输出文件名。
settled  — 执行器确认的真实结局：completed / failed / cancelled，
           带停止原因、结束时间、投递给模型的 t1 文本。
closed   — 执行器缺席时由运行时代为宣告的结束，带 cause 说明为什么。
```

**一个 job 恰好有一条闭合记录**，是 `settled` 或 `closed` 二者之一。

`settled` 与 `closed` 的分工是本设计里一条重要的措辞纪律：**任何一处读到 `closed` 就立刻知道「这不是 job 自己跑完的」**，不需要再去比对别的字段。把两者合并成一个带布尔标记的终态会丢掉这个即时可读性。

### 3.3 cause

```
resume    — 进程重启后发现它开着，而上一个运行时已经不在了
navigate  — 导航到某个分支点后发现它开着，而这个运行时不认识它
dispose   — 拥有它的 agent 正在被销毁
fork      — 它是被 fork 出来的新会话继承的，那里没有任何东西在跑
abort     — 请求中止后执行器始终没有确认
```

cause 写进记录本身。它不增加成本（一个字段），但让事后排查和 `read_job` 能区分「用户杀的」「运行时崩的」「所在分支被 fork 走的」。五种成因合并成一个 `interrupted` 会丢掉这个信息。

### 3.4 reducer 丢弃没有头的记录

一条 `settled` 或 `closed` 记录，如果链上没有同一个 job 的 `started`，直接丢弃，不凭空造出一个身份没人记录过的 job。

这条规则在现有 journal 里已经存在，它在这里正好保证：导航到 job 启动之前的分支后，即使这个 job 后来在别处结束并写下记录，它也不会出现在这条分支的 job 表里。

## 4. 闭合规则

### 4.1 一条规则

> **闭合分支上开着、而当前运行时不认识的 job。**

四个场景都是它的实例：

| 场景 | 「不认识」等于 |
|---|---|
| resume | 内存里一个都没有，等于全部 |
| navigate | 内存里没有的那些；还活着的留着继续跑 |
| dispose | 内存里那些正要死，等于全部 |
| fork | 新会话里什么都没在跑，等于全部 |

`dispose` 与 `fork` 是特例：此刻「不认识」退化成「全部」。

### 4.2 navigate 不能无条件闭合

从当前叶子导航回一个更早的分支点，那时开着的 job **可能此刻仍在这个进程里跑着**——导航不杀进程。无条件闭合会关掉活的 job。

因此闭合必须以「这个运行时的内存里有没有它」为判据，而不是以「分支上看起来开着」为判据。这也是为什么闭合不能做成 persistence 框架的通用钩子：框架看不见运行时内存。

### 4.3 触发时机是「即将写这条分支」，不是「落到这条分支」

只看不续的导航不应该在树上留下痕迹。闭合记录永远写在**即将被延长的那条分支**上。

### 4.4 fork 的闭合发生在新会话里

fork 不碰源会话，源会话的 job 继续跑。新会话继承全部状态，同时为其中每一个开着的 job 写入 `closed(fork)`。子会话递归 fork，每一层各自闭合自己的。

新会话里的「abort」不是发信号——那里没有进程——而是在记录上宣告它已中断。

## 5. 输出文件

job 的 stdout 不进对象。对象是不可变值，装一个无界增长的字节流是错的。

- 每个 job 一个输出文件，放在 `core:jobs` 自己的 namespace 目录下。
- `started` 记录里存**相对文件名**，不存绝对路径。绝对路径在 fork 之后会指向源会话目录，这是必须避免的自足性破坏。
- 文件名用 `toolCallId` 而不是 `jobId`。jobId 是进程内计数器，重启后会撞进上一轮的文件；toolCallId 在一个会话内不重复。
- 大小上限复用运行时已有的输出上限配置，从只管内存流扩展到同时管磁盘文件，超限行为沿用现有语义（请求终止运行方，不截断结果）。

### 不可变性的一次有意识的弱化

persistence 契约要求 state root 不可变。这里记录本身是不可变的（「这个 job 的输出在某个文件里」），但它点名的文件是 append-only 且还在增长。

精确的措辞是：**一条旧分支永远不会看到更少，只会看到更多。**

这是对不可变性的弱化，必须写在实现的模块注释里，不能默认。fork 时复制一个正在写的文件会得到一个撕裂的前缀——那恰好就是崩溃留下的状态，重放路径本来就要处理它。

## 6. 顶层接口

只描述形状，不含实现。

### 6.1 namespace 定义

`core:jobs` 是一个常规的 `PersistenceNamespaceDefinition`：

- `forkPolicy` 为 `degrade`——job 的历史值得带走，它的活进程不值得。
- 实现 `fork`，在目标会话里为每个开着的 job 写 `closed(fork)`。
- 不使用 `locate`。job 状态严格属于会话，默认布局就是对的。
- `openStorage` 返回下面的自定义 storage。

### 6.2 自定义 storage

`core:jobs` 不能直接用默认对象日志，因为它要做两件默认实现不做的事：沿链 reduce，以及连输出文件一起复制。

它包住默认对象日志，覆写两个方法：

- **解析**：沿依赖链回溯，reduce 成 job 表返回，而不是返回单条记录。
- **复制闭包**：先委托默认实现复制对象，再把这批记录点名的输出文件复制进目标目录。

其余方法直接委托。

### 6.3 闭合

一个纯函数形态的能力：

```
输入：当前分支解析出的 job 表、运行时认识的 job 集合、cause
输出：需要追加的闭合记录（可能为空）
```

它有三个调用点，共用同一段逻辑，写出的记录形状完全一致。fork 钩子是它的一层薄包装。

### 6.4 与运行时的接口

background runtime 现有的 `openOwnerJournal` 端口形状保持不变——runtime 不认识 persistence，也不能自己写 ref（分支只有 harness 能写）。端口的实现内部做两步：写对象拿到 ref 数据，再经 harness 追加到分支。

runtime 继续只知道「我追加了一条记录，成功或失败」，现有的 `degraded` 健康度策略原样保留。

ref 究竟由谁写、以什么形状开放给 namespace，是一个不限于 background 的问题，单独写在 `docs/ZH/persistence-ref-writer.md`。本节第二步指的就是那份文档里的 `commit`；第 4 节那条「即将写这条分支」的触发时机对应它的反向通道。

## 7. 前提

**一个会话同时只有一个活进程。**

这条前提让 resume 时的闭合无歧义：分支上开着而内存里没有的 job，其执行器必然已经不存在。

它的直接后果是**删除 epoch**。现有实现用 `(epoch, jobId)` 做键，是因为 jobId 是进程内计数器、跨运行会撞。改用 `toolCallId` 做键之后——它在一个会话内不重复——epoch 不再有存在理由。

如果将来允许同一个会话被两个前端同时打开，resume 时的闭合会关掉另一个进程正在跑的 job，届时需要额外的活性判据，那是一次独立的设计。

---

## 8. 时序

### 8.1 t1 投递与闭合记录的顺序

**先追加 t1 消息，再写闭合记录。**

中间崩溃只会导致下次重复投递一条 t1（无害）。反过来会导致记录声称已投递而模型从未收到（有害）。

### 8.2 dispose 的约束

闭合 ref 只能经 harness 写，而 dispose 要拆掉 harness。**闭合必须发生在 harness 关停之前**，挂在既有的 shutdown 生命周期上。写晚了等于没写。

### 8.3 resume 的位置

闭合与 t1 投递发生在 agent 变得可路由之前。一个迟到的结果在那之后到达，就是一条消息而不是上下文。

## 9. 分期

### v1

单会话内完整正确：启动与闭合记录、跨 resume 恢复、`read_job` 能读到历史 job。

**fork 不在 v1。** 原因是 `JsonlPersistenceRepo` 目前没有任何生产调用方，运行时仍在用旧的会话目录仓储，两者目录命名规则不同、互相看不见。而 v1 需要的只是 ref 模式、分支投影和对象日志这三样纯工具，不需要仓储的会话生命周期与 fork 闭包。

**约束**：v1 的 namespace 目录必须落在与新仓储一致的相对位置（会话目录下的 persistence 子目录里）。这样 v2 迁移时只是会话目录改名，namespace 目录原地不动，v1 写下的 ref 和对象无需改动。

`navigate` 的闭合可以推迟到 v1 之后。不做的最坏后果是导航回去之后一个已死的 job 看起来还开着，下一次 resume 会收拾它。

### v2

session-manager 迁移到 `JsonlPersistenceRepo`，fork 随之生效。v1 已经写好的复制闭包实现届时直接起作用。

## 10. 这套设计买到了什么

除了消除 t0 的歧义，还有一件事是顺带的、但价值独立：

**`read_job` 与 `list_jobs` 跨 resume 可用。** 现在 job 表只在内存里，进程一重启，模型对一个老 job 的查询只会得到「未知 job」——哪怕它早就跑完、输出还在盘上。状态落到分支之后，对历史 job 的查询有了答案。

而这也解释了为什么状态必须在**分支**上而不是在 sidecar 里：一条被回退掉的分支不应该看见另一条分支起的 job。

---

## 11. 明确不做

- **不持久化 report 和 abort 请求。** 结构化进度报告高频、可丢、只对活着的进程有意义；abort 请求不改变「欠不欠」这个事实，它的确认就是闭合记录本身。两者都留在内存。
- **不读兼容旧的 sidecar 日志。** 它只对旧会话有意义。恢复路径必须只有一条真相——同时维护两份可能不一致的状态，是需要额外调和逻辑的直接来源。
- **不把闭合提成 persistence 框架的契约。** 闭合依赖「运行时内存里有没有它」这个框架看不见的事实，属于框架明确划归调用方的激活决策。目前只有一个 namespace 需要它。等第二个真实实现出现，再从两个实现里抽形状。往定义接口上追加一个可选方法不是破坏性变更，晚做的成本接近零。
- **不给闭合记录设计撤销。** 分支是 append-only 的，一条记录写下就永远在那条分支上。要「取消闭合」，正确的动作是回退。
